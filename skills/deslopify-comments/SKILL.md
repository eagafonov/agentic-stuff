# Deslopify Comments

## Overview

Coding agents leave behind "comment slop": comment blocks that narrate the editing
session instead of documenting the code. They describe what *used to be* there, what
was *just changed*, or restate the line below in English.

This skill reviews **comments only** and rewrites them so each surviving comment
explains **why the current code is in its current state**.

## Scope Discipline

- Touch **comments and docstrings only**. Never change executable code, strings,
  identifiers, formatting, or imports.
- Do **NOT** build, compile, lint, or run tests. Assume the code is valid and correct.
  Comment-only edits cannot break it.
- Do not "improve" the code you happen to notice. Report it in the summary instead.
- Never delete license headers, copyright banners, SPDX tags, codegen markers
  (`// Code generated by ...`, `# noqa`, `# type: ignore`, `eslint-disable`,
  `nolint`, `pragma`, `#!/...` shebangs) or doc-tooling directives.
- Never delete `TODO`, `FIXME`, `HACK`, `XXX`, `SAFETY`, `NOTE:` markers that carry
  real information. `HACK`/`SAFETY` comments explaining *why* are the good kind.

## Slop Patterns to Remove or Rewrite

**Change-history narration** (remove — that's what git is for):
```
// Previously we used a map here, but now we use a slice
// Changed from sync.Mutex to atomic
// Removed the old validation logic
// This replaces the deprecated helper
// Added in the refactor
// NEW: ...  /  UPDATED: ...  /  (was: ...)
```

**Restating the code** (remove — the code already says it):
```
// Increment counter
counter++

// Loop over users
for _, u := range users {

// Constructor
func New() *T {
```

**Section-divider theatre** (remove unless the file genuinely needs navigation):
```
// ============================
// HELPER FUNCTIONS
// ============================
```

**Conversational / apologetic / self-congratulatory** (remove):
```
// Note: I chose this approach because it's cleaner
// This is a bit hacky but works for now  (no explanation of what/why)
// Let's make sure we handle the error properly
// Great — now the value is validated
```

**Tutorial padding** (remove — explains the language, not the code):
```
// defer runs when the function returns
// nil check to avoid panic
```

**Redundant docstrings** that only echo the signature (trim to nothing, or make it
say something):
```
# process_data processes the data
# Args:
#   data: the data
```

**Over-commented obviousness**: if more than ~1 comment line per 5 code lines and
none of them add information, thin them out.

## Comments to KEEP (and improve)

Keep anything a future reader could not derive from the code:

- **Why**, not what: `// Retry 3x — upstream returns 503 during rolling restarts`
- Non-obvious constraints: units, ranges, invariants, ordering requirements
- External references: ticket IDs, RFCs, vendor bug links, spec sections
- Workarounds pinned to a cause: `// Workaround for libfoo <2.1 leaking fds (issue #431)`
- Concurrency/lifetime/ownership contracts
- Public API docs (godoc / docstrings / JSDoc) that describe contract, params,
  errors, side effects — tighten wording, do not delete
- Deliberate non-obvious choices: `// Linear scan: n < 8 in practice, beats hashing`

**Rewrite rather than delete** when a slop comment hints at real knowledge:

```
// Previously this used json.Unmarshal but that broke on large numbers
->
// Uses a decoder with UseNumber: json.Unmarshal loses precision on int64 IDs
```

## Process

1. **Determine the file set** — from a commit/range, the staged index
   (`git diff --cached --name-only --diff-filter=d`), the unstaged worktree
   (`git diff --name-only --diff-filter=d`), all pending changes
   (`git diff HEAD --name-only --diff-filter=d`), a path, or the caller's request.
   Skip vendored, generated, and third-party paths. If the set is empty, say so and stop.
2. **Read each file** and locate every comment block.
3. **Classify** each comment: keep / rewrite / delete, using the rules above.
4. **Edit** with precise, minimal replacements — one file at a time, comments only.
   When deleting a standalone comment block, delete its line(s) entirely (and the
   now-orphaned blank line if it leaves a double blank).
5. **Verify scope**: `git diff -- <file>` and confirm every changed line is a comment
   line. If any non-comment line changed, revert that hunk. When the target was the
   staged index, compare against the index (`git diff -- <file>` already does this) so
   you only review your own comment edits, not the pre-existing staged changes.
6. **Report** a summary table.
7. **Staging/committing**: follow the caller's instruction exactly.
   Default when nothing is specified: leave changes in the working tree, unstaged,
   uncommitted, and say so. If the input was staged changes, warn that leaving edits
   unstaged splits each file across index and worktree, and offer to `git add` exactly
   the files you edited (never `git add -A`).

## Ambiguity Rule

If a comment might encode knowledge you cannot verify from the code (a business rule,
a vendor quirk, a perf measurement), **keep it** and list it under "Kept, suspicious"
in the report. Deleting real knowledge is far worse than leaving one weak comment.

## Report Format

| File | Removed | Rewritten | Kept as-is |
|------|---------|-----------|------------|
| path/to/file.go | 7 | 2 | 11 |

Then:
- **Notable rewrites** — before/after for anything non-trivial
- **Kept, suspicious** — comments you left because you could not verify them
- **Code smells noticed** — reported only, never fixed

## NEVER

- Change non-comment code
- Run builds, tests, or linters
- Delete license/copyright/SPDX/codegen/tooling directives
- Delete a comment because you don't understand it — ask or keep it
- Commit or stage unless explicitly told to
